# OAuth providers

Provider adapters keep protocol-specific account retrieval separate from application identity. A provider email is not automatically proof that two different provider accounts should be merged; select an account-linking strategy deliberately and enforce its database uniqueness assumptions. See `../src/oauthProviders.ts`, `../src/accountStrategy.ts`, `./user-adapter.md`.

A first sign-in creates an account only from an email the provider vouches for; otherwise anyone could squat a victim's address. GitHub's profile email carries no verified flag, so the address comes from GitHub's verified email list. Microsoft's `mail` is set by the tenant's administrator, so it is trusted only when the app is bound to one tenant: under `common`, `organizations` or `consumers` any tenant could assert any address, so new Microsoft users are refused there.

An email is not an identity, so an OAuth account is bound to the provider's stable user id (ADR 0086). Sign-in looks up that id first, so an account follows its owner when the email changes at the provider; the stored email is kept, because the provider's new value may be unverified. Only when no account carries the id does the email decide, and then an email match may sign in only if the account is unbound and the provider verified the email, which binds it; an account bound to another id is refused even with a verified email. That is what stops an admin of another Entra tenant from setting `mail` to a user's address and signing in as them. A provider without a stable id key keeps the email-only matching, so a custom provider should set one. Under `'unified'` one row serves several providers but stores only its own provider's id; other providers link to it by verified email alone, as before. Because the email still finds accounts without a binding, it belongs to the provider; the reference settings flow refuses to change it rather than orphaning the account or letting a stolen session rebind it.

Bind authorization callbacks with server-generated, single-use state and validate return URLs before redirecting the newly authenticated browser. The provider callback origin and public frontend origin can differ; do not turn a relative redirect into an attacker-controlled backend URL. Extra provider session data is visible to that user's browser; keep secrets out. Provider-supplied names are untrusted text and must be safely rendered wherever used. Source: `../src/login.ts`, `../src/redirectResolver.ts`, `../../server/src/httpRoutes/authCallbackRoute.ts`.
