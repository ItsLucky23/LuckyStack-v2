# Server security boundaries

**Origin is not identity.** HTTP requests with an explicit disallowed Origin/Referer are rejected; state-changing requests without either are rejected rather than trusting the caller-controlled Host header. Origin-less read-only probes remain possible. CORS response headers are not permission to skip route authorization. For testing browser-like writes, supply an allowed `Origin` header. Source: `../src/httpHandler.ts`, `../../core/src/checkOrigin.ts`.

**Cookies need CSRF protection.** Browsers attach cookies automatically; state-changing framework and custom routes must verify a token before execution unless covered by narrowly scoped auth bootstrap or signed-webhook exemption. With a session, compare to its CSRF token; without login use the double-submit contract. Do not log the token in mismatch hooks. Explicit bearer-mode credentials do not use the same ambient-cookie trust model. Source: `../src/httpRoutes/csrfMiddleware.ts`, `../src/httpRoutes/csrfRoute.ts`, `../../core/src/extractToken.ts`.

**Exemption is not authentication.** A route exempt from origin/CSRF checks must verify a signature or equivalent credential itself; an exemption must not make cookie-protected data readable by arbitrary origins. Keep OAuth state validation and redirect allowlisting intact (`../src/originExemptRegistry.ts`, `../../login/src/login.ts`). Security-header customizations must not silently remove required protection (`../src/securityHeadersRegistry.ts`).

**Boot warnings matter.** Login-bootstrap and OAuth-callback routes cannot present a pre-existing CSRF token; their exemption depends on restrictive session-cookie SameSite policy. Relaxing that policy without a replacement origin/CSRF defense enables login CSRF. The unauthenticated health endpoint can reveal fingerprints of synchronized environment secrets: do not publish plain unsalted hashes, and do not assume a per-boot keyed hash protects low-entropy values from an attacker who can read its public boot identifier. See `../src/verifyBootstrap.ts`, `../src/httpRoutes/healthRoutes.ts`.

**Test reset fails closed.** Its mode and secret checks exist to prevent test-only state deletion in live environments. Do not loosen either condition. Custom session adapters must clean up their own test state; the built-in reset cannot know their storage. See `../src/httpRoutes/testResetRoute.ts`.

**A scoped reset is exact, and a bad selector is an error.** The unscoped reset also deletes every framework session, including the one an authenticated test sweep runs on, so the reset accepts a target selector and the test-runner always narrows it to rate limits. A selected reset runs exactly the listed targets; an unknown or empty target is rejected rather than silently resetting nothing or everything. Changing the unscoped reset instead was rejected because CI setups rely on it to log users out between suites (ADR 0064). The valid targets live in one list in core that server and runner both read; a new target belongs there so the two sides cannot drift. Source: `../../core/src/testResetTargets.ts`.
